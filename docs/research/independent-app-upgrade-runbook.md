# iO Agent 独立安装包升级手册

更新：2026-11-04。当前官方底座 1.0.10/258，自有版本 dev169/10591，包名 `cn.cznbnb.ioagent`。本模式独立的是安装身份和数据空间，仍依赖原厂 Flutter、Android SDK 和服务；不是完全独立实现，也不会自动跟随官方 App 更新。

## 给接手 Agent 的执行顺序

1. 读 AGENTS.md、交接顶部、当前 candidate/rollback 元数据和本手册。fetch 后核对 Claude 合入情况，使用自己的工作区。操作手机、眼镜、问答前拿设备锁，保留正式配对；不要用全局 Desktop 启动覆盖。
2. 从已核实官方来源取得新版底包，记录下载来源、版本、完整 SHA、官方证书、更新说明。先归档当前小型契约证据，再分析新底包；不能用改白名单的方式跳过适配。只查更新不能顺手刷固件。
3. 对照下表检查安装身份和原厂契约。新宿主应建立对应版本的适配定义，重新确认类、方法、字段和接收回调；混淆名存在不代表行为相同。`host-110.mjs`、`voice-110.mjs`、`build.mjs`、`NavReflect` 和原厂 HTTP/native 输入边界是当前入口。
4. 只运行受影响测试及必要共存回归。现有命令：`python3 tools/android/test-manifest.py`、`node tools/android/test-host110-policy.mjs`、`node tools/android/test-agent-card.mjs`、`node tools/android/test-task-presentation.mjs`。资料/待办变动再跑对应 `test-lifelog-calendar-http.mjs`、`test-native-todo.mjs`、`test-native-todo-runtime.mjs`。版本固定的输入/期望应根据真实新版证据调整，不能删检查让测试通过。
5. 走现有 `tools/android/build.mjs` 和 `sign.mjs`。保持自有持久签名；官方私钥不在项目中，改包不能保留官方签名。来源、DEX 成员、私密资源、签名和对齐审计必须通过。不编入对方未提交源文件。
6. 用手机实际安装 APK 的完整 SHA 确认差异基线，`apk-delta.py` 生成补丁，手机用 `ApkDelta.java` 对应 DEX 重建，校验目标 SHA 后正常安装。核对版本/签名/完整 SHA、资料和配对未丢失；不清数据、不绕过系统安装验证。
7. 真机按下表验收。服务器保存、SDK 回调成功、手机预览、镜片实际显示分别记录；自动测试不能替代实机。当前正在智记录音时，不为验证随意停录、开新采音、删真实资料或发真实短信。
8. 更新证据、人工验收待办、交接并提交推送。仅保留当前和一份回退 APK，迁移保护与旧机例外按既有记录处理；清理本批手机补丁/诊断工具，释放设备锁。没有通过的项目保持开放。

## 必查兼容点

| 项目 | 自动检查/适配依据 | 真机出口与当前已知边界 |
|---|---|---|
| 包名与证书 | 独立 provider、私有权限、动作、回调 alias、taskAffinity；保留实现类 | 新装/更新、登录、分享回调；不能伪造原厂证书或换全局身份字符串 |
| 首次配对与版本查询 | Java 与 Flutter 更新源相同端口；独立包 18795 | 与原厂/旧包共存时查询正常，无错误更新循环；dev166 已修端口冲突 |
| 资料/待办 HTTP | 原始与已知修改后 native 库 SHA、签名入口、完整正文大小 | 日期正文、同步、导出；dev167 修复漏登记新 native SHA，不再误报宿主未适配 |
| Agent 通知 | business21/type2 的真实序列化字段；任务寿命取 command_expires_at | 只发自有通知，SDK 回执与镜片观察分别取证；dev169 用户已确认收到 |
| 问答/提词器/口述 | 收发分发体、回调注册和整稿 ACK、卡片互斥 | 正文显示、退出/口述/确认；不能用短卡成功代替整稿验收 |
| 主手机与会话 | 同账号恢复、共享默认、租约、断网队列 | 两包/两机不能重复投送；已结束会话不得伪装在线 |
| 天气一次定位 | 独立包使用原厂 Android system one-shot；缓存/超时/取消/退避不变 | dev169 手机预览恢复 29°C；镜片天气仍须观察。室内首次定位可能较慢 |
| 持续定位/地图/导航 | 依赖第三方包名+证书鉴权，不能沿用原厂身份冒充成功 | **未解决**：独立包 AMap 持续定位仍有 code8/初始化失败。一次天气修复不覆盖轨迹、导航或地图服务 |
| 通知来源 | 原厂推荐列表 + 实际收到通知时登记 appSettings | 原厂 1.0.10 有自动登记来源逻辑，非全量已安装 App 清单；用户要求此行为保留 |
| 短信回复 | 原厂 MAP 蓝牙消息访问申请和眼镜状态响应 | 初查 MAP 未连接；用户随后确认短信通知打开。未发送真实短信，不把打开开关当发送验收。普通通知权限与 MAP 不同 |
| 原厂待办/日程 | 对照 create DTO 与眼镜事件序列化，不能混用 | 待办有 dueDate/dueTimeZone；日程有 startTime/endTime/location；建议卡 timeRange 不等于待办地点字段 |
| 账号/分享/支付等外部 SDK | 清单及第三方注册身份按实际功能检查 | 未走过的路径不宣称兼容；登录成功不代表微信回调、支付、导航都通过 |

## 自动化能省什么，不能代替什么

现有脚本已负责构建、签名、差异传输和多处契约门禁，手册把散落的入口、验收和失败历史集中。小更新且契约未变时可重复同一流程；原厂重构或第三方身份授权变化时，仍需分析和适配。当前不再增加一套通用升级框架，也不许诺一键支持未知新版。

原厂功耗对照可保留两个独立包，测其中一个时在系统中强行停止另一个。无需为了比较立刻改回包名；更换回原厂包名仍使用自有签名，既不能修复第三方官方签名绑定，也不能覆盖正版安装。真正的官方签名只属于未修改的原厂 APK。


## 设置中的成品更新（dev172）

`tools/android/publish-app-update.py --notes <JSON数组文件> --out <回执文件> --apply` 只发布已装机且完整摘要匹配的签名APK；不上传私钥。默认不带apply只检查，远端上传临时文件会清理。公开清单在 `/io-updates/latest.json`，只保留当前和上个发布包。手机只在用户点检查/下载时联网，核对包名、版本码、SHA与现装签名后调用系统；第一次需用户允许安装更新，不能自动放开系统校验。

本轮只在原厂1.0.10底座验证此入口。当前AppRelease还对发布清单的host_version做1.0.10匹配；跨底座更新前须先升级这个清单兼容检查并验收，不直接发布新底座给旧检查器。下载/系统内升级待下个合法更高版验证，不制造假版本。眼镜固件仍采用Fixed60已有精确候选与门禁，不将手机成品更新当作通用固件补丁器。

长等待接口部署需同时核对App/电脑超时和Nginx。dev172使用25秒watch，公网网关为该单独路由设35秒；只改Node等待值会被旧15秒网关切断并触发重试。用 `tools/phase1/tune-inbox-gateway.py` 检查/应用，保留配置备份，不改其他API超时。
