# 雷鸟 iO 产品与当前项目调研

> **需求与进展更正（2026-10-10）**：当前产品依据为 [PRD v0.2](./PRD.md)。用户已确认录音链路实现、大部分硬件设置接口可调通；以下旧交付记录和静态观察保留为历史证据，不能据此认定最新录音能力未完成或要求重做。服务器定位已明确为资料存储、查询和消息中转，综合分析及任务执行在电脑本地 Agent；官方基础体验为正式交付门槛。用户当前原 App 智记的说话人、保存/上传限制以其实际反馈为准。

调研日期：2026-10-10。范围：官方公开资料、Turbo-IO 作者资料、当前工作区文档与关键代码静态检查。本轮未操作手机/眼镜、未修改开发代码、未重新运行测试，也未向另一开发聊天发送消息。

## 2. 当前项目基线

- 当前定制实现位于 `rebuild/harmony-sdk`，`ref/Turbo-IO` 为参考资料。
- [现有交付说明](../../rebuild/README.md)记录：0.1.14 已安装，自动重连、状态读取、亮度写入/恢复有真机记录。

- 地图、录音传输、智记断续恢复、提词和长后台仍有待验收事项。存在安装包和页面不代表这些场景可日常使用。

## 3. 与本次目标直接相关的差距

| 项目 | 本次看到的证据 | 产品影响 |
| --- | --- | --- |
| 上传优先级 | [旧计划](../../rebuild/harmony-sdk/docs/PLAN-v2.md)把智记服务器上传放在阶段 3/P2 | 与用户当前核心目标不符，应提升至首个端到端版本 |
| 上传实现 | [UploadService](../../rebuild/harmony-sdk/entry/src/main/ets/UploadService.ets)为一次性 multipart 上传每日 Markdown 和音频；HTTP 2xx 即报告上传 | 有原型基础，尚非可靠分段同步；需持久化确认、重试去重、进度和恢复 |
| 自动上传 | [JournalPanel](../../rebuild/harmony-sdk/entry/src/main/ets/pages/JournalPanel.ets)保存自动开关和时间，并提示“每天自动上传”；扫描当前 entry 源码，仅找到设置读写和页面内上传调用，未找到消费该配置的调度逻辑 | 界面承诺超出当前可观察实现；不能把保存配置当作任务已运行 |
| 上传范围 | 同页 dayAudio 只收集 lifelog 的 OGG；每日文字汇总可以包含主动录音 | 主动录音原音未通过该每日路径一起上传；PRD 必须分别列原音和文字 |
| 智记切段 | [LifelogSession](../../rebuild/harmony-sdk/entry/src/main/ets/LifelogSession.ets)有分段、持久化开启状态和重连恢复；默认 clockAlign=true、clockStepMinutes=60 | 源码默认按整点切段，尽管另有 10 分钟 segmentMs；不能用单个默认数值误判实际切段行为。实时上传需与长段归档解耦 |
| 转写时机 | [RecordingService](../../rebuild/harmony-sdk/entry/src/main/ets/RecordingService.ets)智记自动转写默认等充电；主动录音优先 | 适合离线回顾的策略，无法直接满足白天及时上下文 |
| 音频清理 | 同文件按本地文字就绪清理超过 3 天的智记原音 | 自有服务器目标下需增加服务器原音持久化校验，避免尚未上传就清理 |
| 断连补录 | 智记有断连封口、重连续录；处理 163/164 音频。当前实现未找到主动 167 缓存补拉发送 | 自动恢复录制不能证明断连期间没有缺失；旧逆向文档记载的命令仍需独立实测 |
| 通知下发 | [NotificationSession](../../rebuild/harmony-sdk/entry/src/main/ets/NotificationSession.ets)有 business 21 文本发送及同 UID 回报；当前限制标题 16、正文 48 字 | 是局部设备通道原型，限制属于当前实现，不能当作已确定硬件上限；没有证明服务器到眼镜全流程 |
| 通知反馈 | 同文件收到 type 4/cmd 只更新状态说明，未输出服务器事件 | 有候选观察入口；需验证每个 cmd 语义和上下文关联，不能宣称已识别点头/摇头 |
| 通知重连 | 同文件断连后清空 enabled/peer/uid，要求重新应用开关 | 日常自动通知还需明确恢复策略，不应要求每次回页面手动准备 |
| 头势能力 | [DeviceFeatures](../../rebuild/harmony-sdk/entry/src/main/ets/DeviceFeatures.ets)有头部控制设置写入 | 设置开关与实时动作上报不是同一能力；全局手势/原始 IMU 未确证 |
| AI 与智记 | [AppRuntime](../../rebuild/harmony-sdk/entry/src/main/ets/AppRuntime.ets)已有语音前暂停智记、轮次结束后恢复的路由 | 可复用会话协调基础，但需验证真实暂停缺口、恢复和整天覆盖 |
| AI 与 Agent | [VoiceSession](../../rebuild/harmony-sdk/entry/src/main/ets/VoiceSession.ets)调用云 ASR 和模型；目前未在所查主链发现通用电脑任务桥 | 模型回答不等于电脑执行任务；需单列 Agent 生命周期和权限 |
| 后台 | [BluetoothBackground](../../rebuild/harmony-sdk/entry/src/main/ets/BluetoothBackground.ets)申请蓝牙后台任务；[ProbeSession](../../rebuild/harmony-sdk/entry/src/main/ets/ProbeSession.ets)据授权选择后台保留；[ConnectedServices](../../rebuild/harmony-sdk/entry/src/main/ets/ConnectedServices.ets)部分初始化循环要求前台 | 既不是“完全没有后台”，也不能认为“全天后台已通过”；需分开验证蓝牙、网络接收、恢复和任务调度 |

以上为限定源码范围的静态观察，不是对所有目录、历史版本或另一开发 AI 最新工作的全面审计。

## 4. 为什么只靠继续写代码容易偏离目标

这是本轮基于资料的判断，并非对另一开发者能力的评价：

1. “替代官方”同时包含硬件适配、日常产品体验、自有服务器和 Agent 协作四类工作，旧计划未按这次的核心场景排列。
2. 一些需求只有按钮或配置的描述，没有定义数据何时到服务器、用户何时知道成功。
3. 逆向线索、模拟测试、协议回执、镜片效果和长时间可靠性容易被统称为“已实现”。
4. 当前离线转写/留存默认值有其原始用途，但没有围绕实时 Agent 上下文重新设计。
5. 官方 SDK 的适配范围以及可回传的头势尚有未知项，需求清楚也不能消除硬件验证工作。

## 5. 初轮提出的能力验证（按 v0.2 调整）

现有录音与硬件接口优先复用已有验收证据，只对增强带来的影响做回归。新增验证重点调整为原厂通道承载选择/自由语音回复、请求与会话关联、本地 Agent 恢复，以及后台消息接收；下表不构成重建已有录音链路的指令。

| 验证 | 方法 | 成功/失败怎样影响需求 |
| --- | --- | --- |
| 智记音频可靠接收 | 先短录，再锁屏 2 小时，保存帧/片段记录与实际回放证据 | 决定能否进入全天测试，不以命令 ACK 代替音频 |
| 眼镜离线缓存 | 录入可识别时间标记，断蓝牙，再重连检查可回收范围 | 决定能否承诺断连补录；不支持则显示缺口 |
| 自有通知 | 从测试服务器生成通知，手机后台接收并发镜片，人工核对 | 区分网络、后台和设备显示故障 |
| 通知动作 | 每种动作在明确卡片上下文重复测试，关联 UID 与操作回报 | 决定可提供哪些语义确认，是否能保留原始动作类型 |
| 采集与显示共存 | 分别测试智记/主动录音/AI 对话时下发通知 | 决定排队规则以及是否影响主录音 |
| Agent 任务 | 测试任务创建、离线、恢复、取消和重复反馈 | 决定适配器契约，不把聊天模型返回当执行完成 |

这些是后续开发与设备验收计划，本轮没有执行。

## 6. 原 App 对照表如何补全

固定一部参考手机、原 App 版本、眼镜固件和账号配置，逐个记录：用户场景 → 手机入口 → 眼镜操作 → 成功反馈 → 离线/拒绝权限/业务冲突行为。优先走查主动录音、智记和助手，再查其余功能。

正式对照表需为每项标记“原功能已观察 / 仅公开说明 / 当前代码存在 / 真机通过 / 暂不支持”。当前公开资料能建立功能目录，但不足以承诺像素和交互的完整 1:1。

PRD 中的上传周期、保留时间、延迟指标和动作映射属于建议方案，不能作为已经验证的官方能力或用户既定偏好。
