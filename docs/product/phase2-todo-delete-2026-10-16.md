## 用户操作与状态

待办卡增加单条删除确认。确认等待后重新核对条目 ID、修订、归属和内容摘要；切页、进入后台或条目变化后，旧确认不会继续删除。删除记录每批显示 10 条，可回到首批或继续翻页；目录变化时要求重新读取。

| 状态 | 实际含义 | 后续操作 |
| --- | --- | --- |
| local_deleted | 纯本机条目已移出活动列表，原条目留在删除记录 | 尚未发送，可撤销 |
| pending | 已持久保存向原眼镜删除的意图，尚未尝试发送 | 原蓝牙身份认证就绪且 App 前台时首发，未发前可撤销 |
| sending | 已持久保存发送尝试，正在提交消息 | 不提供撤销 |
| submitted | 蓝牙发送调用完成 | 仍需单独核对眼镜实际状态 |
| uncertain | 发送异常、租约变化或进程丢失，可能已经写出 | 不自动重放，明确确认后才重试 |
| cancelled | 撤销了未发送的删除，原条目以新修订恢复到活动列表 | 旧引用不能再次操作恢复后的条目 |

累计最多 3 次发送尝试。重试绑定同一 operation_id、原条目和当前 state_sha256，不生成另一条删除来掩盖未知结果。已提交或可能已发出的删除不能假装撤回。

## 原厂消息边界

静态依据为[原厂协议核对](../../rebuild/phase1/todo-delete-stock-protocol-audit-2026-10-16.json)。认证后的 business 22 仅增加严格单 ID 的 type 7 放行，保留原握手、MTU、认证和其他业务限制。实际命令固定为：

```json
{"eventType":1,"scheduleTotal":0,"todoTotal":1,"eventIDList":[101]}
```

101 仅为文档示例。代码使用选定条目的实际正整数 ID，不提供批量删除、空列表清空或任意业务字节入口。

type 14 回报必须 sourceType 为 7 才进入删除观察。successCount 没有成功条目 ID，因此只记为同一 peer 的未归属操作回报；failList 明确带本 ID 时记录失败码，仍不把未知发送改成确认成功。

type 15 全量查询、type 16 分批回报沿原厂字段处理。观察器要求完整计数、有序批次、稳定 chunk、终包、逐批条数和总数一致，完全相同的重复包不重复计数；冲突、缺字段、超时或断线均不能推出条目已删除。最多 64 批、400 项、256 KiB 归一化内容。协议没有回显查询 UUID，所以完整观察中的 absent 也只表示本轮未见。

原厂 schema 的未知字段、负错误码或超出已支持范围的数据被拒绝为观察输入；这不表示所有固件版本均已适配。未经当前固件真机验证，不能称已调通删除功能。

## 资料保存与恢复

LocalWorkspace 原有待办、稿件和助手对话仍使用同一偏好文件。普通修改保持 v1；首次删除先把此前完整原始字符串保存到 data_v1_backup 并 flush，再将主数据迁移到 v2 并 flush。v2 保存备份 SHA256、原条目快照、删除操作 ID、尝试数、状态和观察记录。

若备份已写完而 v2 主写入中断，冷启动只在主 v1 与已存备份逐字节一致时接续；下一次授权修改先完成 v2 迁移。任何不确定存储结果停止后续写入，不能继续覆盖。迁移不重建原库，也不清除原始备份。

删除记录持续拦截同 peer、同 ID 的迟到完成状态和全量查询条目，避免断线后重新导入已删除条目。冷启动发现 sending 只展示为 uncertain，不自动发送第二次。不同 peer 的回报不能替代原条目发送结果。

当前身份以规范化蓝牙地址为准，只适用于仍保持原验证绑定的场景。同一副眼镜地址变化后，旧记录保持待发；没有可信身份迁移和自动改绑机制。新地址的查询条目也不能自动证明旧记录归属。

删除历史最多 200 条，包含撤销记录，不自动清理。达到上限或主数据接近 1.9M 字符时安全拒绝新写入；归档、导出和历史回收仍需后续实现，不能称完整的长期待办生命周期。

84和94的来源清单中 LocalWorkspace 原文件 SHA256 均为`da3964d8d4b14339cc296acf68cbad90a16efcfb59fba6748a27214df50b7490`，该旧实现只接受 v1，不能直接读取迁移后的待办、稿件和对话 workspace。保留的 0.1.84 安装包可在首次 v2 迁移前作为应用回退；迁移后应保留当前 v2 和原备份，优先恢复支持 v2 的版本。不能直接用旧备份覆盖主数据，否则可能复活已删待办并丢失迁移后的稿件或对话。录音和资料库等独立存储需另行核对，不把本条解释为全 App 资料丢失。

## CLI 接口

schema1–9 保留；schema10 使用 todo 选择器，64 KiB 总回执上限不变。

| 命令 | 输入与作用 |
| --- | --- |
| todo-list | scope 为 active 或 deleted，limit 为 1–10，游标绑定当前目录摘要；只读 |
| todo-delete | 显式 tdel 操作 ID、四字段 reference 和 --confirm，保存选定单条删除意图 |
| todo-delete-status | 只读同一 operation_id 的当前状态 |
| todo-delete-cancel | operation_id 和 state_sha256；只允许撤销尚未尝试发送的操作 |
| todo-delete-send | operation_id、state_sha256 和 --confirm；显式发送或重试 |
| todo-query | 向当前已认证连接请求全量元数据，记录分批观察 |
| todo-query-status | 只读当前查询状态，不重新发送 |

reference 包含 id、revision、peer、content_sha256。操作 ID 必须显式提供，方便在丢回执后查询同一删除记录。控制命令完成只表示调用返回；reconcile 只读原命令回执，不刷新业务状态或重发。需要最新业务状态时使用 todo-delete-status。
