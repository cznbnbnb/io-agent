## 五、踩雷清单（都踩过，别再踩）

**ArkTS / 鸿蒙**
- `@Builder` 里 `Row {`（裸尾随闭包）**会炸解析**，必须写 `Row() {`；@State 一行一个。
- `catch (e) { throw e; }` 编译不过（arkts-limited-throw），要 `throw new Error(...)`。
- **ArkTS 的 `Intl.DateTimeFormat().resolvedOptions().timeZone` 不可信**（实测报 America/Chicago 而偏移是 +8）。
- `Intl` / `formatToParts` 等能力一律 try/catch 包住，缺能力就回退。

**协议 / 眼镜**
- 眼镜序列化里未用字段是 `mode:0`/`data:""`，不是 null；写入照它的形状来。
- 眼镜现值可能超出"官方档位"（`led_light=1`、`display.height=1`）：写别的字段时**原样透传**，别顺手钳制。
- 回执类型映射：t6=设置回显、t3=状态推送、t4/t1=读应答；**判"写入生效"看内容变化或同 cmd 的 t6/t3**。
- **不要批量轰击眼镜**（历史教训：连发 11 条探测让它懵 4 分钟才自愈）；单项写 + 读回是正确节奏。
- 眼镜时钟会**暂存**官方 APP 曾设过的时间；验证我们自己的 sync_time 必须用 ±1h 跳变观察。
- 写入红线：不碰 factory_reset / OTA / 解绑。新写入先在可逆设置上验证。

**UI / 状态**
- 设置页**永远不要用旧缓存重刷控件**（本 bug 的根因）；用内容版本号判定"真收到新数据"。
- 密集点击：写入走即发队列即可，**不要**用 8 秒 ack 窗口阻塞（历史"上一条指令仍在等待回执"就是这么来的）。
